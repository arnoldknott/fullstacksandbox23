# PostgreSQL

PostgreSQL stores application entities, hierarchies, access policies, and access logs. The backend accesses it through asynchronous SQLModel and SQLAlchemy sessions, manages schema changes through the Alembic trees under [backend/src/migrations](../../backend/src/migrations/), and configures local and test services through the root Docker Compose files.

## Schema migration workflow

Use the existing `postgres_migration_*.sh` scripts to generate, check, and apply future migrations rather than hand-authoring revision files or bypassing the wrappers with direct Alembic commands.

| Operation | Development | Stage/production |
| --- | --- | --- |
| Generate from model changes | [revision script](../../backend/scripts/dev/postgres_migration_revision.sh) | [revision script](../../backend/scripts/stage_prod/postgres_migration_revision.sh) |
| Check schema against models | [check script](../../backend/scripts/dev/postgres_migration_check.sh) | [check script](../../backend/scripts/stage_prod/postgres_migration_check.sh) |
| Apply pending revisions | [upgrade script](../../backend/scripts/dev/postgres_migration_upgrade.sh) | [upgrade script](../../backend/scripts/stage_prod/postgres_migration_upgrade.sh) |
| Downgrade | [downgrade script](../../backend/scripts/dev/postgres_migration_downgrade.sh) | [downgrade script](../../backend/scripts/stage_prod/postgres_migration_downgrade.sh) |

Run the development scripts inside the backend container through the existing Compose workflow, and validate the development migration in the test environment. Stage/production revisions for model-driven changes are autogenerated by the pipeline: do not generate or add those revisions manually in advance.

Only add manual stage/production revisions for changes the scripts cannot generate, such as custom data migrations. Their upgrade and downgrade operations must match the development migration verified in the test environment; only history-specific metadata may differ. No separate execution of stage/production migrations in the test environment is required. Keep all environments synchronized with the verified development changes through the deployment workflow.

Alembic automatically generates revision IDs in every environment. These IDs identify migrations and link their revision histories independently of Git. Development migration filenames use the generated Alembic revision ID and do not need a Git commit hash (`COMMIT_SHA`). For stage/production, the GitHub Actions pipeline supplies `COMMIT_SHA` for migration naming and logs; no manual assignment is needed.

Development uses `alembic.ini` and `migrations/dev`; stage/production uses `alembic_stage_prod.ini` and `migrations/stage_prod`. Follow each tree's actual head. Development revisions are intentionally gitignored and local; stage/production revisions are tracked.

Review autogenerated upgrade and downgrade operations before applying them. Preserve the format from each tree's `script.py.mako`: formatting/lint directives, creation metadata, typed revision identifiers, and generated filename convention. Review constraints, indexes, and data-preservation requirements explicitly; autogeneration is a starting point, not a substitute for review.

Once a revision has been applied, do not change its revision ID, parent revision, or operations in upgrade() or downgrade(). Further database changes require a new revision.
