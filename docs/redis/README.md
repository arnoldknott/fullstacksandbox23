# Redis

Redis supports cached sessions and tokens, Socket.IO message coordination, and Celery transport. Runtime configuration and access-control-list templates live in [cache](../../cache/), while service wiring and environment-specific settings are defined by the application and Docker Compose configuration.

Planned authentication-cache encryption and compatibility rollout are described in the [LinkedIn authentication and account-linking implementation plan](../architecture/security/linkedin-account-linking-plan.md#f-compatible-encrypted-cache-persistence). Session JSON path access is retained; provider credentials and necessary authentication-derived metadata are encrypted at the application boundary. Responses from authorized third-party endpoints, including LinkedIn UserInfo and Microsoft Graph, must never enter Redis, even encrypted; see the global [third-party data storage rule](../../AGENTS.md#third-party-data-storage).

The planned format records the encryption-key version, nonce, ciphertext, and mandatory authentication tag. Both servers load the current and previous versions of one environment-specific Key Vault secret at startup using `Get` and `List`; key material stays in server memory. Routine rotation uses the existing deployment chain, backend first, with temporary authentication failures accepted during the transition. See [key generation and startup configuration](../architecture/security/linkedin-account-linking-plan.md#key-generation-and-startup-configuration) and [routine rotation](../architecture/security/linkedin-account-linking-plan.md#routine-rotation-and-deployment).
